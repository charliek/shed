# Upgrade Guide: v0.9.0 to v0.10.0

v0.10.0 does three things. A server can take its users from a remote **account service**, as
well as from its own config. A server can run each shed as a **cloud VM**, as well as on the
server host. And the separate credential daemon, **`shed-host-agent`, is removed**: the
desktop app is the only credential broker. That removal is the first of several
simplifications.

v0.10.0 is a **clean break**. Old installs are not carried forward: nothing migrates an old
state directory, setting or certificate. This guide tells you what to hold, uninstall,
reinstall, enrol again and edit, in order. In this release:

- **Two auth modes.** `auth.mode: token` (and its older spelling `secure`) and
  `allow_insecure_exposure` are gone. An `open` server binds loopback only; anything reachable
  from another host runs `mtls`.
- **Users.** An optional `auth.users` list gives every key to one named user, who sees and
  enters only their own sheds. A server with no list works as before: one implicit user.
- **Users from an account service** (`auth.directory`, optional). The server enrols with the
  service, pulls its list, and asks for the `directory:read` scope by name.
- **Sheds as cloud VMs** (`default_backend: remote`, optional and experimental). The desktop
  app now shows a cloud shed's `starting` and `stopping` states and the reason beside a status.
- **The credential source.** On each server, each user's credential requests go to one of
  their machines.
- **The signing check.** A machine signs only an SSH login as `git` and a git signature,
  unless you allow more.
- **`git` is reserved** as a shed name. **GitHub logins are pinned** to their account id.
- **`shed-host-agent` is retired.** The desktop app (macOS and Linux) is the only credential
  broker. Credentials are answered only while it runs, and it turns on Launch at login at its
  first launch.
- **A new broker state directory.** The app keeps its state in a new place, so each machine
  enrols again as a new machine.
- **A CLI entry is held to one user.** Every entry is enrolled again once. New:
  `--identity-file`, `--allow-user-change`, the `User:` line and the `USER` column.
- **The SSH front door** for a server that faces the internet: limits on connections that
  have not logged in, a log line when a key is proven, and the peer's address on every
  `SSH auth` line.
- **The audit log** names a person as kind `user` (not `admin`) and the server's own actions
  as kind `system`, and records a person's entry into a service client's shed.
- **For service clients:** `/api/info` reports the exec limits (`exec_limits`), and every
  shed record carries `isolation` and `arch` (`uniform_shed_record`).
- **From the unreleased 0.9.1** (folded into this release): opt-in mount selection, the
  isolated network, service clients and HTTPS exec, the audit log and `state_dir`; fixes for
  #409, #284, #410, #412, #304 and #109; craze 0.2.0 in the images.

!!! warning "Before you start"
    - **Upgrade servers first.** A 0.10.0 CLI or desktop app cannot use a 0.9.x server.
    - **Until then, hold the CLI and the app** on every machine that only uses servers
      ([Hold your client packages](#hold-your-client-packages)).
    - **On macOS, upgrading a server from 0.9.0 stops every running VZ shed once**
      ([macOS (VZ): running sheds stop once](#macos-vz-running-sheds-stop-once)).
    - **Coming from a version before 0.9.0?** Do the [v0.8.2 to v0.9.0
      guide](v0.8.2-to-v0.9.0.md) first.

## Who is affected

### By server auth mode

| Your server today | What v0.10.0 does at start | What to do |
|---|---|---|
| `auth.mode: token` | Refuses to start: `auth.mode: "token" was removed in v0.10.0; use auth.mode: mtls (clients re-enroll with a certificate on their next request), or remove auth.mode for an open server on loopback` | Switch to `mtls` on 0.9.x first ([step 1](#1-move-a-token-or-secure-server-to-mtls)) |
| `auth.mode: secure` | Refuses the same way, naming `"secure"` | The same |
| `open` reachable off loopback (`allow_insecure_exposure: true`) | Refuses to start: `config key "allow_insecure_exposure" was removed in v0.10.0; an open-mode server binds loopback only. Use auth.mode: mtls to reach the server from other hosts` | Switch to `mtls`, or bind loopback ([step 2](#2-move-an-open-server-off-the-network)) |
| `open` on loopback | Starts as before | Nothing for the mode; the credential source and the signing check still apply |
| `mtls` | Starts as before | Nothing for the mode, unless a key under `auth:` is misspelt or cased differently (now refused, see [Troubleshooting](#troubleshooting)) |

A user list (`auth.users`) needs `mtls`. An `open` server always has one implicit user.

## The order: servers first, then every machine right after

A 0.10.0 CLI or desktop app refuses a certificate that names no user, and only a server
older than 0.10.0 issues one. A 0.10.0 server refuses a broker that does not say which
machine it is, and no released `shed-host-agent` or app older than 0.10.0 does. So each
side needs the other at 0.10.0:

| Your machine | Server | Result |
|---|---|---|
| CLI or app 0.10.0 | 0.9.x, `mtls` | **Refused.** The CLI says `the server issued a certificate that names no user: it runs a shed-server older than 0.10.0; nothing was saved. Upgrade the server to 0.10.0, then retry.`, or, for an entry it enrolled earlier, `entry "devbox" cannot be used: its certificate names no user (issued by a shed-server older than 0.10.0); no request was sent. Enrol it again: shed server update devbox --refetch`. The app shows `server "devbox": the server issued a certificate that names no user (a shed-server older than 0.10.0); it was not used. Upgrade the server, then restart the app.` |
| CLI or app 0.10.0 | 0.9.x, `open` | Not supported. An open server is on loopback after [step 2](#2-move-an-open-server-off-the-network), so its clients run on the same machine: upgrade them right after it |
| App 0.9.x, or any `shed-host-agent` | 0.10.0 | **Refused** on every credential request, so that machine's sheds get no SSH agent, AWS or Docker credentials (the message is below) |
| CLI 0.9.x | 0.10.0 | Not supported. Upgrade the CLI right after the server |
| 0.10.0 | 0.10.0 | Works. The credential source applies |

The refusal an old broker gets from a 0.10.0 server, a `403` with this body:

```json
{"error":{"code":"SOURCE_MACHINE_ID_REQUIRED","message":"this server lets one machine per user answer credential requests and needs to know which machine is asking (headers X-Shed-Machine-Id and X-Shed-Machine-Name), but this request named no valid machine; install the current shed desktop app"}}
```

The server logs it once per key: `credential bus: refused a request with no valid machine id
... install the current shed desktop app on that machine; logged once per key`.

The order:

1. **Hold your client packages** on every machine that runs no server
   ([Hold your client packages](#hold-your-client-packages)).
2. **Do the Before you upgrade steps** on every server, while it runs 0.9.x
   ([Before you upgrade](#before-you-upgrade-on-09x)).
3. **Upgrade every server** ([Upgrade servers](#upgrade-servers)). On a machine that runs a
   server, the CLI comes in the same package (`shed` on Homebrew, `shed-server` on apt), so do
   that machine's client steps right after. If such a machine also uses other servers, upgrade
   those first or at the same time.
4. **Right after, on every machine, in this order:**
    1. Quit the desktop app.
    2. [Remove the old credential daemon](#remove-the-old-credential-daemon).
    3. Release the holds and upgrade the CLI.
    4. Enrol every entry again and restart tunnel daemons ([Your CLI entries](#your-cli-entries)).
    5. Upgrade the desktop app and launch it ([The desktop app](#the-desktop-app)).

Between steps 3 and 4, sheds on an upgraded server get no SSH agent, AWS or Docker
credentials from a machine not yet upgraded. Remove the daemon before you upgrade the app: a
0.10.0 server refuses the daemon, and removing it first leaves nothing old running. Enrol
the CLI entries before the app's first 0.10.0 launch, so the app needs no restart.

The signing check starts with the app's upgrade. If sheds `ssh` as another username, set up
[Allowing another username](#allowing-another-username) when you upgrade the app.

## Hold your client packages

Do this on 0.9.x, before any server is upgraded, on every machine that uses a server it does
not run. A routine `brew upgrade` or `apt upgrade` would otherwise move the CLI to 0.10.0
and lock you out of your 0.9.x servers.

macOS (the `shed` formula carries the CLI and the server):

```bash
brew pin shed
```

Linux (the `shed-server` package carries the CLI; hold `shed-desktop` too if it is installed):

```bash
sudo apt-mark hold shed-server
sudo apt-mark hold shed-desktop
```

On a Mac, do not press **Check for Updates…** in the desktop app. It never updates by itself.

Release the holds in step 4 of [the order](#the-order-servers-first-then-every-machine-right-after):

```bash
brew unpin shed
```

```bash
sudo apt-mark unhold shed-server
sudo apt-mark unhold shed-desktop
```

## Before you upgrade (on 0.9.x)

### 1. Move a token or secure server to mtls

Do this on 0.9.x, one change at a time, so a client that cannot follow shows up while you can
still switch back.

1. Set the mode and keep an SSH key source (`auth.ssh.github_users`, `authorized_keys` or
   `authorized_keys_file`); `mtls` refuses to start without one:

    ```yaml
    auth:
      mode: mtls
      ssh:
        github_users: [alice-gh]
    ```

2. `mtls` serves HTTPS only, on `https_port` (default `8443`), and no plain-HTTP listener.
   Open that port wherever clients reach the server.
3. Validate, then restart the server (`sudo shed-server --config /etc/shed/server.yaml
   config-validate` on Linux).
4. On every client, run one command against the server (`shed -s devbox list`). A client
   since v0.8.1 re-enrolls with a certificate on its next request, with no `shed server add`.
   Check each desktop app, the phone app and any service client too.
5. Find what used a bearer token (`curl -H "Authorization: Bearer ..."` in scripts or CI) and
   move it to a client certificate or a [service client](../guides/orchestrated-sheds.md); see
   [Scripts and their keys](#scripts-and-their-keys).

Certificates, enrollment and the CA are described in [Security › mTLS
mode](../reference/security.md#mtls-mode), including what a client older than v0.8.1 sees.

### 2. Move an open server off the network

An `open` server reachable from other hosts needs `allow_insecure_exposure: true` on 0.9.x,
and v0.10.0 refuses that key. Either switch it to `mtls` as in step 1, or bind it to loopback:
remove `allow_insecure_exposure` and set `bind_address: 127.0.0.1` (or remove
`bind_address`, which defaults to loopback).

### 3. Delete or recreate a shed named `git`

A machine signs logins as `git` by default, so that git over SSH works, and on a shed server
the SSH username is the shed's name. A shed named `git` could therefore be opened with a
signature every machine gives out. v0.10.0 refuses to create one and refuses SSH to an existing
one, and warns at start: `WARNING: a shed named "git" exists. "git" is now reserved: SSH to it
is refused. Snapshot it and recreate under another name, or delete it.`

Recreate it under another name (Firecracker and VZ), before or after the upgrade:

```bash
shed stop git
shed snapshot create git git-copy
shed create git-box --from-snapshot git-copy
shed delete git
```

`--from-snapshot` cannot be combined with `--repo` or `--image`; add `--local-dir` or
`--mounts` again if the old shed had them. On the remote backend there are no snapshots:
copy what you need out of the shed and delete it. A 0.10.0 server still lets you list, stop,
snapshot and delete a shed named `git`.

### 4. Decide, per server: no user list, a user list, or an account service

- **No user list** (one implicit user). Every accepted key is an admin and reaches every
  shed, exactly as today. You can keep `auth.ssh` as it is. The credential source and the
  signing check still apply.
- **A user list** (`auth.users`, `mtls` only). Each key belongs to one user, who sees only
  their own sheds. Read [The user list](#the-user-list) before the first start: what happens
  to existing sheds is decided once, on that start.
- **Users from an account service** (`auth.directory`, `mtls` only). The server takes its
  users from a service it enrols with, beside local admins in `auth.users`. See
  [Users from an account service](#users-from-an-account-service).

A 0.9.x server ignores `auth.users`, so write the list in a copy of the config and put it in
place when you upgrade.

### 5. Allow the GitHub API

Every GitHub login (`auth.ssh.github_users`, or `github:` under a user) is now pinned to its
numeric account id at its first fetch, in `{state_dir}/github_pins.json`, and its keys are read
from `api.github.com` by that id. Earlier releases read only `github.com/<login>.keys`.

- The server calls the API for each login at start, at every `auth.ssh.github_refresh`
  (default `1h`) and on `shed users refresh`. Allow `api.github.com` through any outbound
  firewall.
- The requests are unauthenticated, and GitHub rate-limits those per address. A rate limit
  or an outage keeps the last known keys and accepts no new key.
- A login whose account was renamed away, or deleted and registered again by someone else,
  contributes no keys. To follow an account you deleted and created again on purpose, set
  `github_id` under its user.

See [Security › GitHub logins are pinned to their account
id](../reference/security.md#github-logins-are-pinned-to-their-account-id).

## macOS (VZ): running sheds stop once

!!! warning "Upgrading a Mac server from 0.9.0 stops every running VZ shed, once"
    Nothing is lost on disk, but anything running in the sheds ends.

The 0.9.0 `shed-server` started vfkit in the launchd job's process group, and launchd kills
the whole group when the job exits. The `brew services restart shed` that applies 0.10.0
stops the **old** 0.9.0 server, so it still takes the VMs down. From this release on, vfkit
has its own process group and restarts leave VMs running (#409).

Stop the sheds yourself first and start them afterwards:

```bash
shed stop devbox        # for each running shed, before the upgrade
# ... upgrade the server (see below) ...
shed start devbox       # afterwards
```

Also:

- The brew service needs **Homebrew 6.0.13 or later** for its new `stop_timeout`. Run
  `brew update` first; if you have disabled auto-update, update explicitly.
- A restart can now take up to about 30 s. The server shuts down gracefully, and connected
  desktops or SSH sessions hold the drain open.
- If the VZ store is on an external drive (`/Volumes/...`), macOS asks **one more time** for
  access, on the first start of the new `ShedServer.app` (#304). Answer it on the Mac's screen
  (Screen Sharing works), or pre-grant Full Disk Access to
  `$(brew --prefix)/opt/shed/libexec/ShedServer.app` in System Settings → Privacy & Security →
  Full Disk Access. Until it is answered, startup waits at the stall line described in
  [Image store on an external drive](../reference/vz-operations.md#image-store-on-an-external-drive).

## Upgrade servers

### macOS (Homebrew) server

`brew upgrade shed` replaces the CLI and the server binary. If you pinned `shed` on this
machine, unpin it first (`brew unpin shed`). Stop running VZ sheds
([above](#macos-vz-running-sheds-stop-once)). Before you restart the service, check the
config with the **new** binary:

```bash
brew update && brew upgrade shed
"$(brew --prefix)/opt/shed/bin/shed-server" --config "$(brew --prefix)/etc/shed/server.yaml" config-validate
brew services restart shed
```

If `config-validate` fails, fix the config first (see [Troubleshooting](#troubleshooting)). A
config that does not load leaves the service down, and the reason is in
`$(brew --prefix)/var/log/shed-server.log`.

The formula now installs `shed-server` inside a signed `ShedServer.app`
([details](#shed-server-ships-as-a-signed-shedserverapp-304)), so macOS asks once more for an
external drive's permission.

### Linux server (apt)

```bash
sudo apt update
sudo apt install --only-upgrade shed-server
```

The package checks `/etc/shed/server.yaml` with the new binary before it restarts the
service. When that check fails it prints

```text
shed-server was upgraded, but /etc/shed/server.yaml did not validate
against the new binary, so the service was NOT restarted (the old
process keeps running). The error was:
```

followed by the error, and leaves the **0.9.x process running** on the replaced binary. Fix the
config, then:

```bash
sudo /usr/local/bin/shed-server --config /etc/shed/server.yaml config-validate
sudo systemctl restart shed-server
```

Running Firecracker sheds keep running across this restart, as they have since 0.9.0.

Three more things change on apt:

- **`/etc/shed/server.yaml` is no longer a dpkg conffile**, so no upgrade prompts about it
  ([details](#serveryaml-is-no-longer-a-dpkg-conffile-109)).
- **A startup stalled on the filesystem now names the path** (#304,
  [details](#startup-waits-visibly-on-an-unreadable-state-directory-304)).
- **The systemd unit changes.** `shed-server` now starts after, and wants,
  `network-online.target` (it ordered after `network.target`). A server that takes its users
  from an account service pulls the list at start, so it needs the network up. The unit,
  `/etc/systemd/system/shed-server.service`, is a dpkg conffile:
    - **If you never edited it**, dpkg replaces it with no prompt.
    - **If you edited it**, dpkg asks once, and an unattended `apt-get -y` upgrade stops at
      that prompt (`end of file on stdin at conffile prompt`), the package left unpacked and
      your edit untouched. To avoid the stop, add `-o Dpkg::Options::=--force-confold` to the
      upgrade: it keeps your unit and leaves the package's as
      `shed-server.service.dpkg-dist`. Then add `network-online.target` to your `After=` and
      `Wants=` lines.
    - **To recover from an upgrade that already stopped**, run `sudo dpkg --configure
      shed-server` in a terminal and answer the prompt. If you take the package's version
      (until then it waits beside yours as `shed-server.service.dpkg-new`), apply your edits to
      it again; if you keep yours, add `network-online.target` as above.
    - Either way, then run `sudo systemctl daemon-reload` and restart the service.

A unit written by `shed-server install` (a server installed without the package) is not
rewritten by an upgrade of the binary. Run `sudo shed-server install` again, or add
`network-online.target` to its `After=` and `Wants=` lines and run `sudo systemctl
daemon-reload`. This is recommended for a server that takes its users from an account
service, and not required for others.

## Remove the old credential daemon

Do this on every machine that ran `shed-host-agent`, right after the servers it answered for
run 0.10.0, and before you upgrade the desktop app. Nothing replaces the daemon but the
desktop app. Its Homebrew formula has been **removed from the tap**, so `brew install
shed-host-agent` no longer finds it; `brew uninstall` still removes the copy you have.

Quit the desktop app first.

### First, decide whether to keep its config

The app reads `~/.config/shed/extensions.yaml`. It never reads the Homebrew path,
`$(brew --prefix)/etc/shed/extensions.yaml`.

Homebrew always installed that file: the formula wrote it from the example config at the
first install and never overwrote it. Having the file does not mean you changed it. Compare
it with the example:

```bash
diff <(curl -fsSL https://raw.githubusercontent.com/charliek/shed/v0.9.0/configs/extensions.example.yaml) "$(brew --prefix)/etc/shed/extensions.yaml"
```

If you do not recognise the differences as yours (an older release's example differs too),
you never edited it: **do not copy it**. With no file, the app uses its own defaults: it
brokers for every server in `~/.shed/config.yaml`, sends SSH approvals to the app (set in
Preferences › SSH approvals), leaves AWS off and denies Docker until configured. An unedited Homebrew file would instead
limit the app to `http://localhost:8080` (its `server:` line turns discovery off), approve
every Docker request without asking, and require Touch ID for SSH on macOS (on Linux it
denies every SSH request).

**If you did edit it**, copy it, then fix the copy before the app reads it:

```bash
mkdir -p ~/.config/shed
cp -n "$(brew --prefix)/etc/shed/extensions.yaml" ~/.config/shed/extensions.yaml
```

In the copy:

- Delete the `server:` line, unless you want the app to broker for that one server only.
- Check `ssh.approval.policy`. `shed-desktop` asks in the app. `biometrics` and
  `biometrics-or-password` use Touch ID on macOS and deny every request on Linux.
- Check `docker.approval.policy` (the example has `approve-all`), `discovery` and
  `logging.path`.
- Delete any `desktop:` block. It belonged to the old Go daemon and does nothing.

## The user list

The syntax, the rules config load enforces, admins and what is admin-only are in the
[Multi-user Server guide](../guides/multi-user-server.md#write-the-user-list) and
[Configuration › Users](../reference/configuration.md#users). In short:

```yaml
auth:
  mode: mtls
  users:
    alice:
      github: alice-gh
      admin: true
    bob:
      keys:
        - key: ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA... bob@phone
          label: phone
```

`auth.users` replaces the key sources of `auth.ssh`: move each GitHub login and key under its
user and remove `auth.ssh.github_users`, `authorized_keys` and `authorized_keys_file`; config
load refuses both at once. Every key that should still work must be listed: the phone app's,
CI's, each person's.

### On a server with existing sheds, start once with only yourself listed

Sheds and snapshots made before the user list have no user. What becomes of them is decided
**once**, on the first start with a user list:

| User list at that first start | Sheds and snapshots with no user |
|---|---|
| Exactly one user | Become that user's, each one logged. A shed with host directories or server mounts becomes theirs only if that user is an admin. Not undone when users are added later |
| Several users | Nothing is given to anyone. An admin can view, stop and delete them; nobody can enter them until an admin runs `shed assign SHED USER` |

`shed assign` refuses a shed that carries host directories or server mounts, with `409
SHED_HOST_RESOURCES`, because the new owner would get those too. On Firecracker and VZ that is
nearly every existing shed: any shed made with the default `--mounts all`, and every shed made
before mount selection existed, counts as carrying server mounts. Only a shed made with
`--mounts none` and no `--local-dir` can be assigned. So with several users at that first
start, most existing sheds can only be recreated. (Remote sheds carry neither and can always
be assigned.)

So, on a server whose sheds are yours:

1. Start v0.10.0 once with a user list that holds **only you, as an admin**. Every existing
   shed and snapshot becomes yours, mounts included. The log says so per shed
   (`Users: shed <name> had no user; it is now user <you>'s (the only configured user; this is
   not undone if users are added later)`) and then `Users: the one-time upgrade step for the
   user list is done and recorded; from now on a shed with no user is given one only by 'shed
   assign'`.
2. Add the other users and restart. Nothing more is given away.
3. For a shed that should be someone else's, they create a new one; an admin can delete the
   old one. A shed is never moved between users.

The step is recorded in a marker, `{state_dir}/users-upgrade.json`. Later starts log `Users: the
one-time upgrade step for the user list ran at <time> (marker <path>); sheds with no user are
not given one automatically, use 'shed assign'`. Every start with a user list also reports what
is left: `Users: found <n> shed(s) with no user (<m> of them carry host directories or server
mounts and cannot be assigned until recreated without them); ...`, with their names at
`log_level: debug`.

Things that run the step again, or look like a first start:

- **Removing the user list.** A start with no user list removes the marker. Sheds keep their
  `user`, and with no list every shed is reachable again by every key. Adding the list back
  runs the step again: with one user, every shed that still has no user becomes theirs.
- **A replaced or restored `state_dir`.** A state directory that is replaced, restored from
  before the marker, or pointed somewhere else while the backend's data stays has no marker,
  so the next start is a first start. Changing backends keeps the marker, which does not name
  a backend.
- **A damaged or unreadable marker** counts as done: nothing is given automatically.

If the server ran v0.10.0 without a user list first, its credential source follows the same
one-time decision: on the first start with a list a single configured user takes over the
source it had, and with several users it is dropped and each user's first machine to connect
is bound.

### If the server does not start: the step did not finish

A first start that did not finish (a shed or snapshot record it could not read, or a stamp
that failed) leaves the marker pending for the one user it began for. The next start resumes
it only while that same user is still the only one in `auth.users` (on a server with
`auth.directory`, the only local admin; the account service's list never counts). With any
other users, **the server does not start**. It stops before it opens a backend, a store or a
listener, gives nothing away and records nothing. Its error names the user and the marker
file, and begins:

```text
the server does not start: the one-time upgrade step for the user list began for user pat and did not finish, and the users in auth.users are now admin, pat (marker "/etc/shed/users-upgrade.json").
```

Take one of two ways forward:

1. **Finish the step.** Put that user back as the only user in `auth.users` and start the
   server again as before, until its log says the one-time upgrade step for the user list is
   `done and recorded`. Change the users only then. Every shed and snapshot with no user
   becomes that user's.
2. **Abandon the step on purpose.** Stop the server's service and start the server once by
   hand, as the same system user and with the same `--config`, with
   `--abandon-user-upgrade` added. Once it has started, stop it and start the service again
   without the flag:

    ```bash
    shed-server serve --config /path/to/server.yaml --abandon-user-upgrade
    ```

    Abandoning gives nothing more away and records the step as done. The sheds and
    snapshots the step had not reached keep no user for good: only an admin can use them,
    `shed assign` gives such a shed to a user, and a shed that carries host directories or
    server mounts can never be assigned, only recreated. The flag is refused at any start
    with no such step, so it cannot stay on a service's command line.

See [CLI › shed-server serve](../reference/cli.md#shed-server-serve) and [Multi-user Server ›
Sheds with no user](../guides/multi-user-server.md#sheds-with-no-user).

## Users from an account service

New and optional: nothing changes for a server that does not set it. With `auth.directory`,
an `mtls` server takes its users from an **account service** that holds people and their SSH
login keys. The server enrols once with a one-time code (`shed-server directory enroll`),
signs in with OAuth 2.0 client credentials and a JWT client assertion, pulls the list every
`refresh` (default `24h`), keeps a copy, and honours it for `trust` (default `72h`) while it
cannot reach the service. `auth.users` beside it holds only the **local admins**: at least
one, each `admin: true`, with keys only. People are then added, changed and removed on the
service, with no restart. The [User Directory guide](../guides/user-directory.md) walks
through it; read [Security › Users from an account
service](../reference/security.md#users-from-an-account-service) first.

What to know before switching a server:

- **It is a fresh start.** There is no migration, and names decide ownership: a list person
  whose name equals an earlier user's receives that user's sheds, snapshots and
  credential-source records. Pick list names no existing shed carries, unless it is the
  same person. The [one-time upgrade step](#on-a-server-with-existing-sheds-start-once-with-only-yourself-listed)
  reads the local admins only: on a server that never had a user list, a single local admin
  receives every shed with no user.
- **No GitHub logins.** A local admin has keys only, and the list has no GitHub member:
  move each person's keys to the service.
- **Certificates issued by a server older than v0.10.0** name no user and are refused on a
  directory server; the client enrols again.
- **Whoever controls the account service controls the host** of every server enrolled with
  it: an admin in its list has an admin's powers there, host directories and server mounts
  included.
- **The host's clock must be accurate**: the trust time is measured on it, and a clock set
  back before the trust time ends extends it.

Moving an installed server, in the User Directory guide:

- **Enrol as the server's own user.** On Homebrew, run `shed-server` as yourself, never with
  `sudo` (which enrols into `/etc/shed`, where the service never looks), and pass the
  service's config: `shed-server --config "$(brew --prefix)/etc/shed/server.yaml" directory
  enroll`. The state goes to `~/.shed/directory/` unless `state_dir` is set. See
  [Enrol](../guides/user-directory.md#enrol).
- **A running server** reads a first enrolment at its next attempt, at most 15 minutes later.
  Restart it, or run `shed users refresh` as a local admin, to read it at once.
- **Keep your sheds** in two starts: once with only yourself in `auth.users`, so the
  one-time step gives them to your list name, then the switch, with the local admin under
  another name. See [Keeping your sheds](../guides/user-directory.md#keeping-your-sheds).
- **Keep the local admin on a backup key**, with one host name and `--identity-file` on each
  entry. See [Keeping the local admin on a backup
  key](../guides/user-directory.md#keeping-the-local-admin-on-a-backup-key).
- **A new person's first login** pulls the list. See [A new
  person](../guides/user-directory.md#a-new-person) and [Facing the
  internet](#facing-the-internet).

For the service's side: it follows the directory contract in this repository,
`tests/directory-contract/` ([Directory Contract](../reference/directory-contract.md)). This
release changes the contract's text, its manifest and two added exchanges, not its wire for
existing exchanges:

- The server now asks for `scope=directory:read` by name in its token request. The service
  must accept it. One that answers `400 invalid_scope` fails every refresh, and the server
  does not retry without the scope.
- An unknown key's login waits at most 8 seconds (it said 20), and the contract states the
  two pull rates.
- Whether a person is listed, and as an admin, may differ per requesting server, and a
  service leaves out a person whose access on a server depends on a restriction that server
  has not declared it enforces.
- Two new exchanges, `token-scope-directory-read` and `token-scope-unknown`, hold a service
  to the scope.

A service built from the contract copies `tests/directory-contract/v1/` again from this
release and runs the two new exchanges.

New for every server: `shed users status` (`GET /api/users/status`, admin) shows where the
users come from; on a directory server, `shed users refresh` pulls the list and exits 1 when
the pull fails.

## Facing the internet

New in every auth mode:

- **Connections that have not logged in are limited.** One that has not authenticated 120
  seconds after it was accepted is closed. At most 100 connections may be unauthenticated at
  once, and at most 10 of them from one address (an IPv4 address, or an IPv6 /64); loopback
  counts like any other address. A connection beyond either limit is closed at once. These
  values are fixed.
- **`SSH auth allowed` is logged when a key is proven**, not when it is offered, once per
  login.
- **Every `SSH auth` line carries the peer's address**, `remote=<host:port>`.
- **New log lines:** `SSH: closed a connection from <host:port> that did not authenticate
  within 120 seconds`, `SSH: refusing connections from <address>: ...` and `SSH: refusing new
  connections: ...` (each at most once a minute), and `SSH auth failed: remote=<host:port>
  user=<name> keys=<n>`, once for each connection that offered a key and closed without
  proving one.

Point fail2ban at the `SSH auth failed`, grace and per-address refusal lines. Never point it
at `SSH auth DENIED`: a person whose agent offers several keys draws several of those before
one logs in.

On a server that takes its users from an account service, an unknown key starts a pull of
the list only under two login names:

- As `_bootstrap` (`shed server add`): at most once a minute while pulls succeed, once every
  15 minutes while they fail. The login that starts the pull waits for it up to 8 seconds,
  and is refused then if its key is still unknown; other such logins are refused at once.
- As the name of a shed that exists on the server: the login is refused at once, and the
  server pulls in the background, at most once every 5 minutes (15 while pulls fail). A retry
  seconds later gets in once the pull has brought the key.

Under any other name an unknown key starts no pull. A server with GitHub logins keeps its
rule.

See [Security › Facing the internet](../reference/security.md#facing-the-internet),
[Security › A new person](../reference/security.md#a-new-person) and [VPS deployment ›
Hardening the SSH surface](../guides/vps-deployment.md#hardening-the-ssh-surface).

## Sheds as cloud VMs (the remote backend)

New, opt-in and experimental. `default_backend: remote` runs each shed as its own Google
Compute Engine VM; `detect` never picks it. **Every remote shed is a billed VM that keeps
running after the server stops.** Remote sheds have no host directories, mounts, snapshots,
reset, image store or egress profiles (`FEATURE_UNSUPPORTED`). They make no credential
requests, so the credential source and the signing check never come into play there; they
get a user like any other shed.

The desktop app shows a remote shed as `starting` or `stopping` while the cloud works, and a
reason beside a stopped shed's status (`stopped (capacity)`), as `shed list` does. It showed
`unknown` before. `shed list` shows `none` for a remote shed's mounts, where it showed `-`,
and every shed record carries `isolation` (`topology` for an isolated remote shed) and `arch`.

See [Remote Backend](../reference/remote-backend.md), and the orchestrated-sheds guide's
[On a directory server or the remote
backend](../guides/orchestrated-sheds.md#on-a-directory-server-or-the-remote-backend): who
can enter a client's sheds, what `isolated` means on each backend, sizing the limits, the
certificate's lifetime, and revoking a client by removing it.

## New, opt-in (since 0.9.0)

Nothing below changes a server until you use it: with no config change, every shed still gets
every server `mounts:` entry and the `open` network, and there is no audit log and no reaper.

- **Mount selection.** `shed create --mounts none` (or `--mounts claude,gh`) picks which of the
  server's `mounts:` a shed gets; the choice is stored and applied on every start. See
  [Security › Mount selection](../reference/security.md#mount-selection).
- **The isolated network** (Firecracker). `shed create --network isolated` gives a shed the
  internet and nothing else: not the host, other sheds, the LAN, the tailnet or the cloud
  metadata service. `network.default_profile: isolated` makes that the default. The host
  needs the `nft` binary (`command -v nft`; `sudo apt install nftables` if it is missing) and
  shed-server must run as root, as the deb's unit does; without them an isolated create or
  start is refused with `503 NETWORK_ENFORCEMENT_UNAVAILABLE`. VZ supports only `open`. See
  [Security › Network profiles](../reference/security.md#network-profiles).
- **Service clients and HTTPS exec** (`mtls`). An orchestrator such as a CI system or an
  agent runner can create, run commands in and delete its own sheds through the API, with a
  certificate from `shed-server client issue` and a policy under `auth.clients`. Commands run
  through `POST /api/sheds/{name}/exec`, which admins can use too. See the [Orchestrated sheds
  guide](../guides/orchestrated-sheds.md).
- **The audit log.** `audit.jsonl`, next to `egress-audit.jsonl`, records service-client
  requests, HTTPS execs, reaps and a person's entry into a service client's shed. It is on
  whenever `auth.clients` is set, or with `audit.enabled: true`.
- **`state_dir`.** One directory for the server's SSH host key, TLS certificate, mtls client
  CA and GitHub key cache. The default is unchanged (`/etc/shed` as root, `~/.shed` otherwise).
- **`shed list -v`** gains `OWNER`, `MOUNTS` and `NETWORK` columns.

Every new key (`auth.clients`, `exec`, `audit`, `network`, `state_dir`) is in the
[Configuration reference](../reference/configuration.md). A config that sets `auth.clients`
outside `auth.mode: mtls`, or has an unknown key under `auth.clients` or `network:`, is refused
at load; see [Troubleshooting startup
rejections](../guides/security-configuration.md#troubleshooting-startup-rejections).

## After the upgrade

### Your CLI entries

Do this on every machine with the CLI, right after the servers it uses run 0.10.0, and
before the desktop app's first 0.10.0 launch.

1. **Use a 0.10.0 CLI on every machine that shares a `~/.shed/config.yaml`.** A CLI older
   than 0.10.0 drops `user` and `identity_file` when it saves the file, and the 0.10.0 CLI
   then refuses that entry until you enrol it again.
2. **Enrol every `mtls` entry again**, once per entry:

    ```bash
    shed server list                      # every entry, with its USER and STATUS
    shed server update devbox --refetch   # for each entry
    ```

    Until you do, the CLI refuses the entry before it sends any request, and `shed server
    list` shows it as `refused`. For an entry whose certificate came from a 0.9.x server (the
    usual case) it says:

    ```text
    entry "devbox" cannot be used: its certificate names no user (issued by a shed-server older than 0.10.0); no request was sent. Enrol it again: shed server update devbox --refetch
    ```

    For an entry written by an older CLI against a 0.10.0 server, or edited by hand:

    ```text
    entry "devbox" cannot be used: its certificate is for user "pat" but the entry records no user (written by a shed CLI older than 0.10.0, edited by hand, or an interrupted or concurrent enrolment); no request was sent. Enrol it again: shed server update devbox --refetch
    ```

    The refetch prints the user the entry is now held to (`  User: pat`, or
    `  User: (implicit)` on a server with no user list). Check that it is the user you
    expect. `shed server remove devbox` and then `shed server add` also work.
3. **If your ssh agent offers keys of two users** on that server, set the entry's key as
   you enrol it again:

    ```bash
    shed server update devbox --identity-file ~/.ssh/id_ed25519 --refetch
    ```

4. **Restart running tunnel daemons** after a refetch. A running daemon keeps the entry it
   started with:

    ```bash
    shed tunnels stop devbox
    shed tunnels start devbox
    ```

What else changed for entries:

- **An entry is held to one user.** A re-enrolment that would change its user fails, naming
  both users, and nothing is saved. To change it on purpose:

    ```bash
    shed server update devbox --refetch --allow-user-change
    ```

    After that, restart long-running `shed` commands, tunnel daemons and the desktop app.
- **`shed server list`** has a `USER` column (in `--json`, `user` and `user_implicit`).
- **The key refusal is reworded.** `shed server add` and `shed server update --refetch` now
  fail with `the server refused every SSH key ssh offered for _bootstrap@<host>: ...`, and the
  bootstrap error reads `sdk/bootstrap: the server refused every key ssh offered (...)`. The
  old texts, `your SSH key is not in this server's allowlist (auth.ssh.github_users /
  authorized_keys)` and `ssh could not authenticate with any available identity (… or the key
  may not be on the server allowlist)`, are gone: scripts that match them must match the new
  ones.
- **An `~/.ssh/config` alias whose `HostName` points elsewhere** enrols over SSH and then
  fails at the API. Use the server's real name with `--identity-file`.

The desktop app follows the same rule: it shows the same user-change refusal under
Preferences › Credential broker. Fix the entry with the CLI, then restart the app. See
[Desktop configuration › The user an entry is held
to](../desktop/configuration.md#the-user-an-entry-is-held-to).

### The credential source

On its first start a v0.10.0 server has no source for anyone, and logs:

```text
WARNING: credential source bindings: no file at <path>, so an empty one was created: no user has a credential source, and the first machine to connect for each user will become that user's source. If this server had bindings before (the file was deleted, or not restored with the rest of the state), every user should check 'shed source status' and move it with 'shed source use' if it is not their machine
```

The first machine to connect for each user (on a server with no user list, for the implicit
user, so for every shed) becomes that user's **credential source** on that server. Start the
app on the machine you want first, or check and move it afterwards:

```bash
shed source status                  # which machine is the source, and is it connected
shed source ls                      # every machine that has presented itself for you
shed source use laptop              # make that machine the source (its name or id)
```

or press **Use this machine** in the desktop app's Preferences on the machine you want.

- **A second machine** is refused as `not-source`. Its Preferences name the source on that
  server's row, with **Use this machine**, and it keeps retrying without enrolling again.
- **A move** ends the old machine's streams at once and drops the requests it was holding:
  an approval waiting there is lost. The app's button connects at once.
- **Nothing fails over.** While the source is asleep, off the network or not running the
  app, its user's sheds get no answer, and the tool in the shed fails at its own timeout.
- **An admin** can see and move another user's source with `--user`, among that user's own
  machines.
- **A script key** cannot be a source or move one.

The full rules are in [Credential Source](../extensions/source-binding.md) and [Security ›
One machine answers for each user](../reference/security.md#one-machine-answers-for-each-user).

#### A machine restored from another machine's backup

A machine's id is random, created once, and stored in `machine.json` in the broker's state
directory (see [The app starts as a new machine](#the-app-starts-as-a-new-machine)). A cloned
disk or a restored backup gives two machines the same id; the second to connect is then
refused as a `duplicate`. On the copy, quit the app, delete `machine.json`, and start the app
again: it creates a new identity, which the server sees as a new machine.

### The signing check

A machine signs a request from a shed only if it is exactly one of:

- an SSH login for a username in `ssh.allow_users` (default `git`), with a key that is offered;
- an SSH signature (`ssh-keygen -Y sign`, which git uses for commits and tags) in the namespace
  `git`.

Everything else is refused **before** any approval prompt, and audited in the broker's
audit log (`~/.local/share/shed/extensions-audit.log` by default) with `result: refused`,
`code: SIGN_REFUSED` and the reason, for example `username_not_allowed` with `login
user=deploy`. In the shed, `ssh` reports `signing failed ... agent refused operation`. See
[SSH Agent › What the machine signs](../extensions/ssh-agent.md#what-the-machine-signs).

#### Allowing another username

Add the username to `ssh.allow_users` **and** name the keys that may be used with
`ssh.offer_keys`, in the app's `~/.config/shed/extensions.yaml`. A name other than `git`
without `ssh.offer_keys` fails the broker's config load.

```yaml
ssh:
  allow_users: [git, deploy]
  offer_keys:
    - SHA256:QSbP+oRmKHQkEp2CsJn72x/5Qxyq5lsK6sib0fK1mr0   # as ssh-add -l prints it
```

Quit and reopen the app: it reads `extensions.yaml` when it starts. A file it cannot load
leaves the broker off, and Preferences › Credential broker shows the error.

!!! warning "Do not allow a username that is also a shed's name"
    On a shed server the SSH username is the shed's name. If an allowed username is also the
    name of one of your sheds, code in any of your sheds can get a login signed that opens
    that shed. Only `git` is reserved by the server. See [Security Posture › What the signing
    check does not
    cover](../extensions/security-posture.md#what-the-signing-check-does-not-cover).

### Scripts and their keys

- **A script that called the API with a bearer token** needs a client certificate now. A
  script acting as a person can use a certificate enrolled with a key of theirs (`shed server
  add` writes it under `~/.shed/creds/`); an orchestrator that needs only its own sheds
  should be a [service client](../guides/orchestrated-sheds.md), whose bundle works with
  `curl --cert`.
- **On a server with a user list**, list the key a script uses under the user it acts for,
  with `script: true`. A script key reaches that user's sheds, but cannot take a
  `credentials` certificate, use the credential bus, or see or move the user's credential
  source, so automation never answers or receives the user's credential requests. See
  [Security › Expired keys and script keys](../reference/security.md#expired-keys-and-script-keys).

### What you will notice

No step is needed for these:

- **On a server that takes its users from an account service**, a first `ssh` into an
  existing shed with a newly added key is refused at once, and a retry a few seconds later
  gets in once the server's pull has brought the key. If the service is slow, retry until it
  has.
- **`shed server add`** (or a refetch) with a key the account service does not list yet fails
  after 8 seconds, not as soon as the pull ends.
- **An SSH connection that has not authenticated within 120 seconds is closed**, and at most
  100 connections (10 from one address) may be unauthenticated at once.
- **The desktop app shows a cloud shed that is stopping as `stopping`** (it showed `unknown`),
  and a shed's reason beside its status, as the CLI does: `stopped (capacity)`.
- **On a remote-backend server, `shed list` shows `none` for a shed's mounts** instead of
  `-`, and every shed record carries `isolation` and, where the server knows it, `arch`.

## craze

The `extensions` and `full` images bake craze 0.2.0; 0.9.0 baked 0.1.0. A shed keeps the
craze its image baked, so recreate it from a 0.10.0 image to get 0.2.0.

A machine where you installed craze yourself needs its own upgrade. On macOS run
`brew upgrade craze`. On Linux, upgrade it the way you installed it; see
[craze's install doc](https://github.com/charliek/craze/blob/main/docs/getting-started/quick-start.md#install).
Check with:

```bash
craze --version
```

### End the old hub after an upgrade

A craze hub that was already running keeps the old binary until it exits. It exits by itself
only once no session runs and no client is attached. See it, then end it:

```bash
pgrep -f 'craze hub$'    # prints the hub's pid
pkill -f 'craze hub$'
```

The new craze CLI, and sometimes shed's Resume refusal, also name the old hub's pid. Ending the
hub ends no session; the next client starts a new hub on the new craze. See craze's
[Upgrading while sessions run](https://github.com/charliek/craze/blob/main/docs/getting-started/upgrading.md#upgrading-while-sessions-run).

craze's guide says Homebrew and apt installs need nothing. That holds for starting sessions,
but shed offers Resume only when the running hub can reopen, so for shed an old hub hides Resume
until you end it.

Restarting the hub does not upgrade sessions already running: each keeps the craze it started
with. `/effort` and the settings sheet's `effort → <level>` need a session started on 0.2.0.

The desktop's `--no-start` reach depends on the craze installed on the host, not on the hub:
it runs `craze bridge --hub --no-start`, and a 0.1.x craze that rejects the flag sends the
desktop down the older path. Once the desktop has fallen back for a machine it stays on that path
until you relaunch the app, or remove the machine and add it again.

### What needs craze 0.2.0 on the host

| Feature | craze needed |
|---------|--------------|
| `/effort` and effort facts | 0.2.0, in a session started on it |
| Resume a saved session | 0.2.0, in the running hub |
| The desktop's `--no-start` reach | 0.2.0 installed on the host (a 0.1.x host falls back) |
| The `/` menu, and a name for a new session | 0.1.1 |
| Listing, creating and attaching to sessions | 0.1.0 or later |

## What changed

Fixes since 0.9.0, for reference.

### VZ VMs outlive the server (#409)

vfkit now runs in its own process group, so launchd no longer kills it when the
`shed-server` job exits. The brew service also sets `stop_timeout 35`, so launchd waits for the
server's graceful shutdown instead of sending SIGKILL partway through.

| Situation | Behaviour from 0.10.0 |
|-----------|---------------------|
| `brew services restart shed` | VMs keep running; the new server re-adopts them. |
| `brew services stop shed` | VMs keep running. Run `shed stop` first if you want them stopped. |
| Server cannot come back | VMs run unmanaged until it does. The next start re-adopts them (`resumed message channel` in the log). |
| Ctrl-C on a foreground dev `shed-server` | VMs are no longer stopped. |

### Firecracker stop and delete (#284)

| Operation (running shed, writable mounts) | Before | 0.10.0 |
|---|---|---|
| `shed delete` | about 25 s | about 0.2 s |
| `shed stop` | 25-30 s, then force-kill | about `stop_timeout` (10 s) |

- The shutdown hook and the pre-stop sync now run with mounts still live.
- On both backends, a client disconnect during `shed stop` no longer turns the stop into a force-kill.
- `shed delete` now refuses, and keeps the shed's resources, if its VM survives SIGKILL. Retry once the VM is gone.

Known limits:

- A graceful Firecracker stop still ends at `stop_timeout`. The guest cannot receive
  Ctrl-Alt-Del; a fix is a follow-up. The hook and sync still run before the kill.
- After a Firecracker server restart, running sheds' 9P mounts stay dead until
  `shed stop && shed start` (#369).

### Root-owned `~/.local` and `~/.config` (#410)

Directories a mount needs under the shed user's home are now created as `shed`. Existing
sheds are repaired on their next `shed start`.

A root-owned directory left by a mount you have since removed from config is not on any mount
path, so it is not repaired. Fix it by hand inside the shed:

```bash
sudo chown shed:shed ~/.local ~/.config
```

Add any other affected parents (for example `~/.local/share`) to the command. Images built
from this release also pre-create `~/.local`, `~/.local/bin`, `~/.local/share`,
`~/.local/state`, `~/.config` and `~/.cache` owned by `shed`.

### CLI re-mint (#412)

`shed start`, `shed create`, `shed image pull`, `shed image push`, `shed snapshot create` and
the prune commands now re-mint and retry once on an expired or invalid credential.

### Startup waits visibly on an unreadable state directory (#304)

Before it starts the backend, `shed-server` now reads each of the active backend's state
directories once (`images_dir`, `instance_dir` and its parent, `snapshots_dir`, `uppers_dir`
and `socket_dir`) and logs `Checking state directories: …`. A startup step stalled on the config
or a state directory logs a line naming the path after 10 s, then every minute:

```text
shed-server: startup is still waiting on /Volumes/ext/shed/vz (checking state directory) after 10s. …
```

On macOS the line points at the permission prompt for an external drive and at Full Disk
Access; on Linux it says the filesystem may not be responding. Startup continues on its own
once the directory can be read. A directory macOS has denied gets one warning with the Full
Disk Access fix.

A server whose store hangs on a read (an unanswered prompt, or a filesystem that is not
responding) now blocks startup at that line and does not reach `Shed server is ready` until
the read completes. Before, it reached `ready` when egress was off, and only the background
resume of running sheds hung, with no message. See
[Image store on an external drive](../reference/vz-operations.md#image-store-on-an-external-drive).

### `server.yaml` is no longer a dpkg conffile (#109)

The `shed-server` deb used to ship `/etc/shed/server.yaml` as a dpkg conffile. If you had
edited it and a release changed the packaged template, dpkg prompted. An unattended upgrade
(`apt-get -y` with no terminal) failed at that prompt with `end of file on stdin at conffile
prompt` (exit 100) and left the package unconfigured.

| Operation | Behaviour from 0.10.0 |
|-----------|---------------------|
| Fresh install | Creates `/etc/shed/server.yaml` from `/usr/share/shed/server.yaml.default`. |
| Upgrade, reinstall, remove | Never prompts about `/etc/shed/server.yaml` and never changes it. |
| Purge | Deletes `/etc/shed/server.yaml`. The host key and TLS files in `/etc/shed` stay. |

- **The first upgrade from 0.9.0** marks the old conffile entry `obsolete` in dpkg's database
  (`dpkg-query -W -f='${Conffiles}' shed-server`). This is harmless; dpkg leaves the file alone.
- **The reference copy** is `/usr/share/shed/server.yaml.default`, and every upgrade updates
  it. Your config no longer picks up template changes, edited or not; the server supplies a
  default for any key your config leaves out. To see what a release changed:

    ```bash
    diff /usr/share/shed/server.yaml.default /etc/shed/server.yaml
    ```

- **A host stuck by this failure** shows `iU` for `shed-server` in `dpkg -l` and has an
  `/etc/shed/server.yaml.dpkg-new`. Installing this release as in
  [Linux server (apt)](#linux-server-apt) recovers it: your config is kept and the leftover
  `.dpkg-new` is removed.
- **Rolling back to 0.9.0 or earlier** registers the file as a conffile again, so dpkg asks
  about an edited config. Keep yours without a prompt by adding `-o
  Dpkg::Options::=--force-confold` (see [Rollback](#rollback)). The next upgrade marks the
  entry obsolete again.

### shed-server ships as a signed ShedServer.app (#304)

On macOS, the brew formula now installs `shed-server` inside a Developer ID signed app bundle,
`$(brew --prefix)/opt/shed/libexec/ShedServer.app`.
`bin/shed-server` is a symlink into it, and the brew service still runs
`opt/shed/bin/shed-server`, so existing launchd plists stay correct and the normal upgrade
restart is all that is needed. The formula no longer re-signs `shed-server` ad hoc on install.

macOS keys a bare binary's privacy grant on its absolute path, and brew's Cellar path changes
every version, so an external drive's permission was asked again after every upgrade. A bundle's
grant is keyed on its bundle ID and signature, which are the same for every build, so it
survives upgrades.

The cost is one more prompt, once: the first time the server starts as `ShedServer.app`, macOS
asks again for the external drive, because the identity changed. After that, upgrades don't ask
again unless the grant is revoked or reset. If the server is started from Terminal rather than
the brew service, the prompt names Terminal.

## What changed for API and SDK users

- **Authentication.** No route was removed. The server never issues or reads a bearer token:
  an `Authorization` header is ignored. A `_bootstrap` request with no CSR gets `this server
  requires auth.mode: mtls; upgrade shed (client certificate support)`.
- **Ownership.** Shed and snapshot records carry `user` (also in `shed list --json`). On a
  server with users, another user's shed answers `404 SHED_NOT_FOUND`, an admin's refused
  entry `403 FORBIDDEN`, and an admin-only resource `403 FORBIDDEN` (`admin only: <what>`).
  A name in a `/api/sheds/{name}` or `/api/egress/{name}` path that is not a valid shed name
  answers `404 SHED_NOT_FOUND` before any other check. Creating a shed named `git` answers
  `400 INVALID_SHED_NAME`. See [API › Ownership](../reference/api.md#ownership).
- **New routes.** `POST /api/sheds/{name}/assign` (`409 SHED_ALREADY_ASSIGNED`, `409
  SHED_HOST_RESOURCES`), `POST /api/users/refresh` (with a `directory` row on a server that
  uses an account service), `GET /api/users/status`, `GET /api/sources` and `POST
  /api/sources/use` (`404 SOURCE_MACHINE_NOT_FOUND`, `503 SOURCE_BUSY`). `GET /api/info` lists
  the feature `source_binding`.
- **The credential bus.** Every subscribe and respond must send `X-Shed-Machine-Id` and
  `X-Shed-Machine-Name`. Subscribe can answer `403 SOURCE_MACHINE_ID_REQUIRED`, `403
  SOURCE_NOT_BOUND`, `409 SOURCE_DUPLICATE_STREAM` and `429 SOURCE_RATE_LIMITED`.
  **`409 SOURCE_DUPLICATE_STREAM` replaces `409 NAMESPACE_ALREADY_REGISTERED`**: another
  machine's subscribe is now `403 SOURCE_NOT_BOUND`, and the same machine's duplicate is
  retryable. Respond adds `403 FORBIDDEN` for an answer that matches no pending request (in
  every mode, open included: an answer is no longer delivered by shed name), `413
  REQUEST_TOO_LARGE`, `429 TOO_MANY_RESPONSES` and `503 RESPONSE_NOT_DELIVERED`. None of these
  is a `401`. See [API › Extensions](../reference/api.md#extensions).
- **The Go SDK host client.** `sdk.HostClient` must present a machine identity (the two
  headers, with a stable id and a name for the machine it runs on); a v0.10.0 server refuses a
  client that sends none with `403 SOURCE_MACHINE_ID_REQUIRED`. Pass it with the
  `sdk.WithMachine(id, name)` option; the client never invents one. The server's refusals come
  back as `*sdk.SourceError`. The client follows a redirect only to the configured
  server's own origin. See [Extensions › SDK](../reference/extensions.md#sdk).
- **The broker's client kind.** The app's broker enrols with the client kind `broker` (it was
  `host-agent`), with no alias; the server records it in the certificate. A server older than
  0.10.0 records a kind it does not know as empty and still issues the certificate: nothing
  is refused for the kind. The app's own audit entries say `"source":"broker"` (older lines
  in the same file keep `"host-agent"`).
- **SSH log lines.** `SSH auth allowed` is logged only when a key is proven, every `SSH auth`
  line carries `remote=<host:port>`, and `SSH auth failed` is new
  ([Facing the internet](#facing-the-internet), [Security › The SSH auth
  log](../reference/security.md#the-ssh-auth-log)).
- **The audit log** (`audit.jsonl`). A person is no longer `{"kind":"admin","subject":…}`:
  it is `{"kind":"user","user":"pat","admin":true,"script":false,"subject":…,"serial":…}`,
  with `implicit: true` and no `user` for the one user of a server with no user list. A `reap`
  line carries `"identity":{"kind":"system"}`. A service client is kind `client`, as before.
  There is no alias for the old kind: a filter on `kind == "admin"` matches nothing written
  after the upgrade, and rotated files keep the old shape. A new `ssh` line records each time
  a person enters a service client's shed over SSH (`channel` `shell`, `exec`, `sftp` or
  `tunnel`; never the command), and a new `connect` line each tunnel a person opens into one
  through the HTTPS Connect API. See [Configuration › Audit
  log](../reference/configuration.md#audit-log).
- **`/api/info` reports the exec limits**, under the always-advertised feature token
  `exec_limits`: an `exec` member with `max_stdin_bytes`, `max_timeout_seconds`,
  `max_output_bytes`, `max_concurrent_per_shed`, `max_argv_elements`, `max_env_keys`,
  `max_argv_env_bytes`, `default_timeout_seconds` and `default_output_bytes`. See [API › GET
  /api/info](../reference/api.md#get-apiinfo).
- **One shed record on every backend**, under the always-advertised feature token
  `uniform_shed_record`: every shed record carries `isolation` (`none`, `firewall` or
  `topology`) beside the unchanged `network_profile`, and `arch` (`amd64` or `arm64`) where
  the server knows it. A remote record always carries `"mounts":{"mode":"selected"}`.
  `/api/info` gains `guest_arch` (omitted when the remote sizes mix). See [API › GET
  /api/sheds](../reference/api.md#get-apisheds).
- A client gates on a feature token, never on a version. Nothing a client already reads is
  renamed or removed.

## Rollback

An older server binary does not keep users apart, so a rollback opens every shed to every
key. It also drops the `user` field from any record it saves: a shed's record is saved
whenever the older binary starts, stops or otherwise updates that shed. A 0.10.0 CLI or app
cannot use a server rolled back to 0.9.x (it refuses that server's certificates), so roll
the clients back too, or keep the server on 0.10.0. Do it in this order:

1. **Restrict access first.** Decide who may reach the server while it runs the older
   binary, and keep everyone else out: list only those people's keys in the restored
   `auth.ssh`, or keep the server off the network (bind it to loopback, or close its ports)
   until you are back on v0.10.0. With `auth.ssh` keys back, **every key is an admin again**.
2. **Restore the previous config.** A 0.9.x binary ignores `auth.users`, so an `mtls` config
   without an `auth.ssh` key source refuses to start (`auth.mode: mtls requires at least one SSH
   key source ...`). Put back the config you ran before, with any restriction from step 1. On
   apt, do this before the downgrade: the older package validates the config too, and skips
   its restart when it fails.
3. **Roll back the server.** On apt, if your repository still offers the version
   (`apt-cache policy shed-server` lists what it has):

    ```bash
    sudo apt install --allow-downgrades -o Dpkg::Options::=--force-confold shed-server=0.9.0
    ```

    Homebrew offers only the current formula, so a macOS rollback means installing the
    previous release by hand from its GitHub release page. A remote-backend server cannot go
    back to 0.9.0, which has no remote backend.
4. **Roll back the clients.**
    - **CLI:** take `shed` from the v0.9.0 release's archive on the
      [releases page](https://github.com/charliek/shed/releases) and put it ahead on your
      `PATH`, or on Linux install `shed-server` 0.9.0 as above. A 0.9.0 CLI drops `user` and
      `identity_file` when it saves `config.yaml`.
    - **Desktop app:** install the 0.9.0 app from its release page (updates only move
      forward). It reads the old `host-agent/` state directory if you kept it, else it
      enrols again.
    - **shed-host-agent:** the formula is gone from the tap, so only the v0.9.0 release
      tarball reinstalls it.

What the older binary does with the new files: it ignores `github_pins.json` (it follows
GitHub logins by name again, so a renamed or re-registered login works under it),
`users-upgrade.json` and `source-bindings.json`, and leaves them in place.

**Coming back to v0.10.0**, re-check ownership before you open access again: `shed list` as an
admin shows the `USER` of every shed.

- The marker from the first start is still there, so nothing is given a user automatically.
  A Firecracker or VZ shed the older binary saved has **no user** now: admin-only until
  assigned, and `shed assign` refuses it if it carries host directories or server mounts.
  Such a shed can only be recreated for its owner. A snapshot whose record lost its user stays
  usable and deletable by an admin only; snapshots cannot be assigned. On a server whose sheds
  are all yours, you can instead start once with no user list (which removes the marker) and
  then with only yourself listed, as on the first upgrade.
- On the remote backend the `shed_user` label stays on the VM, and a record with no user
  takes it back from the label at the next read of the VM.
- The credential source bindings are loaded as they were before the rollback.
- Enrol every CLI entry again (`shed server update NAME --refetch`), since a 0.9.0 CLI dropped
  their users.

## Checklist

In the order of [the order](#the-order-servers-first-then-every-machine-right-after):

- [ ] On every machine that runs no server: hold the CLI and app packages (`brew pin shed`;
      `sudo apt-mark hold shed-server` and `shed-desktop`).
- [ ] On every server, while still on 0.9.x: switch `token` or `secure` to `mtls` and confirm
      every client reconnects; move any `open` server off the network.
- [ ] Delete, or recreate under another name, any shed named `git`.
- [ ] Allow `api.github.com` from every server that follows a GitHub login.
- [ ] Per server, decide: no user list, a user list, or an account service. For a list, write
      every user, the admin flags, and every key that must keep working (phone, CI with
      `script: true`). With existing sheds, plan the first start with only yourself listed.
- [ ] macOS servers: stop running VZ sheds.
- [ ] Upgrade each server; validate the config with the new binary before restarting; answer
      the dpkg prompt for an edited unit; confirm it runs v0.10.0.
- [ ] Then on every machine: quit the desktop app.
- [ ] Uninstall `shed-host-agent` (copy its config only if you edited it, then fix the copy).
- [ ] Release the holds and upgrade the CLI.
- [ ] Run `shed server update NAME --refetch` for each entry (with `--identity-file` where
      needed), and check the `User:` line.
- [ ] Restart tunnel daemons.
- [ ] Install or upgrade the desktop app and launch it.
- [ ] Press **Use this machine** where the app is refused as not the source.
- [ ] Delete the old `host-agent/` state directory.
- [ ] Launch at login is on: switch it off in Preferences › General if you do not want it.
- [ ] Check Preferences › Credential broker: each server connected.
- [ ] On machines whose sheds `ssh` as a username other than `git`, add it to
      `ssh.allow_users` with `ssh.offer_keys`, and make sure no shed has that name.
- [ ] With a user list: check the start-up log for sheds with no user, then add the other
      users; recreate sheds that should belong to someone else.
- [ ] On a directory server: `shed users status` shows the list in force.
- [ ] On an account service: its client may ask for `directory:read`; its contract copy is
      this release's.
- [ ] On a server facing the internet: the `SSH auth` lines carry `remote=`; fail2ban matches
      `SSH auth failed`.
- [ ] Audit-log readers: filters match kind `user`.
- [ ] Confirm the orchestrator's service client still runs and the phone app connects.

## Troubleshooting

| You see | Why | Fix |
|---|---|---|
| `auth.mode: "token" was removed in v0.10.0; use auth.mode: mtls ...` (or `"secure"`) | The removed mode | [Step 1](#1-move-a-token-or-secure-server-to-mtls) |
| `config key "allow_insecure_exposure" was removed in v0.10.0; ...` | The removed acknowledgment | [Step 2](#2-move-an-open-server-off-the-network) |
| `bind_address "0.0.0.0" exposes an open-mode server beyond loopback; open mode is loopback only, use auth.mode: mtls to reach it from other hosts` | An open server bound off loopback | [Step 2](#2-move-an-open-server-off-the-network) |
| `auth: yaml: unmarshal errors: line N: field Mode not found in type config.AuthConfig (keys are case-sensitive)` | A misspelt or differently cased key under `auth:` (it used to be ignored, leaving the server open) | Fix the key's spelling and case |
| `config key "Auth" is not recognised; keys are case-sensitive, did you mean "auth"?` | A top-level key cased differently | Use the lowercase key |
| `config key "credentials" was renamed to "mounts"; rename it` | The config still uses the old name of `mounts:` | Rename the key to `mounts:`; the entries keep their shape |
| `auth.users requires auth.mode: mtls` | A user list in open mode | Set `auth.mode: mtls` |
| `auth.users cannot be combined with auth.ssh.github_users: ...` | Key sources in both places | Move each login or key under its user; remove the `auth.ssh` source |
| `the server does not start: the one-time upgrade step for the user list began for user ... and did not finish, ...` | The users changed while the one-time step was unfinished | [If the server does not start](#if-the-server-does-not-start-the-step-did-not-finish) |
| `--abandon-user-upgrade is refused: ...` | The flag at a start with no unfinished step | Start without it |
| `credential source bindings <path>: ...; the server does not start without them, ...` | `source-bindings.json` is damaged, incomplete or from a newer version | Restore it from a backup, or move it aside and restart (each user's next machine to connect is then bound) |
| Server: `WARNING: a shed named "git" exists. ...` | A shed named `git` from before | [Step 3](#3-delete-or-recreate-a-shed-named-git) |
| `403 SOURCE_MACHINE_ID_REQUIRED` (`... install the current shed desktop app`) | A `shed-host-agent`, or a desktop app older than 0.10.0 | [Remove the old credential daemon](#remove-the-old-credential-daemon); [install the current app](#the-desktop-app) |
| The CLI or the app says `the server issued a certificate that names no user` | That server runs a version older than 0.10.0 | Upgrade it ([Upgrade servers](#upgrade-servers)), or keep this machine's packages held |
| `entry "devbox" cannot be used: its certificate names no user ...`, or `... the entry records no user ...`; `shed server list` shows `refused` | The entry was enrolled before 0.10.0, or saved by an older CLI | `shed server update devbox --refetch` ([Your CLI entries](#your-cli-entries)) |
| `the server issued a certificate for user "bob", but entry "devbox" is held to user "pat"; nothing was saved.` | ssh offered another user's key | Set the key with `--identity-file`, or change the user on purpose with `--allow-user-change` ([Your CLI entries](#your-cli-entries)) |
| The same refusal under Preferences › Credential broker | The same, in the app | Fix the entry with the CLI, then restart the app |
| Preferences shows this machine is `not-source` after the upgrade | The app is a new machine, and another id is your source | **Use this machine**, or `shed source use` ([The app starts as a new machine](#the-app-starts-as-a-new-machine)) |
| `not-source: not the credential source for this server; the active source is <name> (<id>)` | Another machine is this user's source | `shed source use`, or **Use this machine** |
| `duplicate: another process with this machine's id already holds namespace ... on this server (duplicate stream)` | A copied state directory, or a stream the server has not ended yet | On a copy, delete `machine.json`. The rest clears by itself |
| In a shed: `ssh-add -l` says the agent refused, and the app is not running | Nothing brokers while the app is closed | Start the app. Launch at login keeps it running |
| The app brokers only for `localhost:8080` | A copied Homebrew config with a `server:` line | Delete the line in `~/.config/shed/extensions.yaml` and restart the app |
| Preferences › Credential broker shows `ssh.offer_keys is required when ssh.allow_users lists users other than "git" (found: deploy)` | Another username without a key filter | Add `ssh.offer_keys` |
| `server devbox does not support credential sources (it needs shed-server 0.10.0 or newer)` | The server still runs 0.9.x | [Confirm the restart](#confirm-the-server-restarted-on-v0100) |
| In a shed: `signing failed ... agent refused operation`; broker audit `reason: username_not_allowed` | A login as a username not in `ssh.allow_users` | [Allowing another username](#allowing-another-username) |
| `Error: failed to create shed: INVALID_SHED_NAME: shed name "git" is reserved` | `git` is reserved | Use another name |
| `Error: shed 'devbox' not found` for a shed that exists | It belongs to another user | Ask its owner, or an admin |
| `shed 'devbox' belongs to another user; an admin can list, stop and delete it but not enter it` | An admin entering another user's shed | Only its user enters it |
| `shed 'devbox' has no user; nobody can enter it until an admin gives it to a user with 'shed assign devbox <user>'` | A shed from before the user list | `shed assign`, or recreate it |
| `409 SHED_HOST_RESOURCES`: `shed devbox carries server mounts, which assigning it would hand to user pat; recreate it without them ...` | The shed has host directories or server mounts | Recreate it with `--mounts none` and no `--local-dir` |
| `409 SHED_ALREADY_ASSIGNED` | The shed already has a user or a service client | A shed is never moved between users |
| An audit-log filter on kind `admin` finds nothing | People are now kind `user` | Match `kind == "user"` |
| `directory: pull failed: token: refused (HTTP 400) "invalid_scope"` | The account service does not accept `scope=directory:read` | Let the service's client ask for `directory:read` ([Users from an account service](#users-from-an-account-service)) |
| `Users: not enrolled` after an enrolment on a Mac | The enrolment ran with `sudo`, into `/etc/shed` | Enrol again as yourself with the service's `--config` ([Users from an account service](#users-from-an-account-service)) |
| A new person's first `ssh` into a shed is refused | The server is pulling the list in the background | Retry a few seconds later |
