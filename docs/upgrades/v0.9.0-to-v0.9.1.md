# Upgrade Guide: v0.9.0 to v0.9.1

v0.9.1 is a fix release. There are no config changes and no wire changes, so mixed client and
server versions keep working. The one exception is craze: the images now bake craze 0.2.0,
and some desktop features need it on the host (see [craze](#craze)). What it fixes:

- **#410** Root-owned `~/.local` and `~/.config` in sheds with nested mounts. Existing sheds are repaired on their next start.
- **#284** Firecracker stop and delete latency with writable mounts.
- **#409** VZ sheds no longer stop when the brew service restarts.
- **#412** The first CLI command after a token-mode server restart no longer fails.
- **#304** On macOS, an external-drive permission now survives upgrades, because `shed-server` ships as a signed `ShedServer.app`.
- **#109** An unattended deb upgrade no longer fails at a prompt about an edited `/etc/shed/server.yaml`.

On macOS, **the upgrade stops every running VZ shed once.** Read
[Before you upgrade (macOS / VZ)](#before-you-upgrade-macos-vz) first.

## Before you upgrade (macOS / VZ)

!!! warning "This upgrade stops every running VZ shed, once"
    Upgrading a Mac from 0.9.0 to 0.9.1 stops all of its running VZ sheds. Nothing is lost
    on disk, but anything running in them ends.

Why: the 0.9.0 `shed-server` started vfkit in the launchd job's process group, and launchd
kills the whole group when the job exits. The `brew services restart shed` that applies 0.9.1
stops the **old** 0.9.0 server, so it still takes the VMs down. From 0.9.1 on, vfkit has its
own process group and restarts leave VMs running.

To control it, stop the sheds yourself first and start them afterwards:

```bash
shed stop <name>        # for each running shed, before the upgrade
# ... upgrade the host (see below) ...
shed start <name>       # afterwards
```

Two more things to know:

- The brew service needs **Homebrew 6.0.13 or later** for its new `stop_timeout`. Run
  `brew update` first; if you have disabled auto-update, update explicitly.
- A restart can now take up to about 30 s. The server shuts down gracefully, and connected
  desktops or SSH sessions hold the drain open. A faster drain is a follow-up.
- If the VZ store is on an external drive (`/Volumes/...`), macOS asks **one more time** for
  access, on the first start of the new `ShedServer.app` (#304). Answer it on the Mac's screen
  (Screen Sharing works), or pre-grant Full Disk Access to
  `$(brew --prefix)/opt/shed/libexec/ShedServer.app` in System Settings → Privacy & Security →
  Full Disk Access. Until it is answered, startup waits at the stall line described in
  [Image store on an external drive](../reference/vz-operations.md#image-store-on-an-external-drive).

## Upgrade steps

### macOS (Homebrew)

```bash
brew update && brew upgrade shed
brew services restart shed
shed version            # confirm 0.9.1
```

### Linux server (apt)

```bash
sudo apt update
sudo apt install --only-upgrade shed-server
```

Running Firecracker sheds keep running across this restart, as they have since 0.9.0.

## craze

The `extensions` and `full` images in 0.9.1 bake craze 0.2.0; 0.9.0 baked 0.1.0. A shed keeps
the craze its image baked, so recreate it from a 0.9.1 image to get 0.2.0.

A machine where you installed craze yourself needs its own upgrade. On macOS run
`brew upgrade craze`. On Linux, upgrade it the way you installed it; see
[craze's install doc](https://github.com/charliek/craze/blob/main/docs/getting-started/quick-start.md#install).
Check with:

```bash
craze --version
```

### End the old hub after an upgrade

A craze hub that was already running keeps the old binary until it exits. It exits by itself
only once no session runs and no client is attached. See it, then end it:

```bash
pgrep -fa 'craze hub$'
pkill -f 'craze hub$'
```

The new craze CLI, and sometimes shed's Resume refusal, also name the old hub's pid. Ending the
hub ends no session; the next client starts a new hub on the new craze. See craze's
[Upgrading while sessions run](https://github.com/charliek/craze/blob/main/docs/getting-started/upgrading.md#upgrading-while-sessions-run).

craze's guide says Homebrew and apt installs need nothing. That holds for starting sessions,
but shed offers Resume only when the running hub can reopen, so for shed an old hub hides Resume
until you end it.

Restarting the hub does not upgrade sessions already running: each keeps the craze it started
with. `/effort` and the settings sheet's `effort → <level>` need a session started on 0.2.0.

The desktop's `--no-start` reach depends on the craze installed on the host, not on the hub:
it runs `craze bridge --hub --no-start`, and a 0.1.x craze that rejects the flag sends the
desktop down the older path. Once the desktop has fallen back for a machine it stays on that path
until you relaunch the app, or remove the machine and add it again.

### What needs craze 0.2.0 on the host

| Feature | craze needed |
|---------|--------------|
| `/effort` and effort facts | 0.2.0, in a session started on it |
| Resume a saved session | 0.2.0, in the running hub |
| The desktop's `--no-start` reach | 0.2.0 installed on the host (a 0.1.x host falls back) |
| The `/` menu, and a name for a new session | 0.1.1 |
| Listing, creating and attaching to sessions | 0.1.0 or later |

## Desktop: if you removed shed-host-agent

0.9.1 does not change this behaviour; the step below is the workaround. In the default `Automatic` broker
mode the app picks between a running `shed-host-agent` daemon and its own in-process broker
once, at launch. If it chose the daemon and the daemon is later stopped or uninstalled, the
app does not fall back, and sheds lose ssh-agent and credential forwarding (`ssh-add -l`
reports "agent refused operation") until the app is relaunched. After removing the daemon,
quit and relaunch the app. A runtime fallback is tracked in
[#411](https://github.com/charliek/shed/issues/411).

## What changed

### VZ VMs outlive the server (#409)

vfkit now runs in its own process group, so launchd no longer kills it when the
`shed-server` job exits. The brew service also sets `stop_timeout 35`, so launchd waits for the
server's graceful shutdown instead of sending SIGKILL partway through.

The trade-offs:

| Situation | Behavior from 0.9.1 |
|-----------|---------------------|
| `brew services restart shed` | VMs keep running; the new server re-adopts them. |
| `brew services stop shed` | VMs keep running. Run `shed stop` first if you want them stopped. |
| Server cannot come back | VMs run unmanaged until it does. The next start re-adopts them (`resumed message channel` in the log). |
| Ctrl-C on a foreground dev `shed-server` | VMs are no longer stopped. |

### Firecracker stop and delete (#284)

| Operation (running shed, writable mounts) | Before | 0.9.1 |
|---|---|---|
| `shed delete` | about 25 s | about 0.2 s |
| `shed stop` | 25-30 s, then force-kill | about `stop_timeout` (10 s) |

- The shutdown hook and the pre-stop sync now run with mounts still live.
- On both backends, a client disconnect during `shed stop` no longer turns the stop into a force-kill.
- `shed delete` now refuses, and keeps the shed's resources, if its VM survives SIGKILL. Retry once the VM is gone.

Known limits:

- A graceful Firecracker stop still ends at `stop_timeout`. The guest cannot receive
  Ctrl-Alt-Del; a fix is a follow-up. The hook and sync still run before the kill.
- After a Firecracker server restart, running sheds' 9P mounts stay dead until
  `shed stop && shed start` (#369).

### Root-owned `~/.local` and `~/.config` (#410)

Directories a mount needs under the shed user's home are now created as `shed`. Existing
sheds are repaired on their next `shed start`.

A root-owned directory left by a mount you have since removed from config is not on any mount
path, so it is not repaired. Fix it by hand inside the shed:

```bash
sudo chown shed:shed ~/.local ~/.config
```

Add any other affected parents (for example `~/.local/share`) to the command. Images built
from 0.9.1 also pre-create `~/.local`, `~/.local/bin`, `~/.local/share`, `~/.local/state`,
`~/.config` and `~/.cache` owned by `shed`.

### CLI re-mint (#412)

`shed start`, `shed create`, `shed image pull`, `shed image push`, `shed snapshot create` and
the prune commands now re-mint and retry once on an expired or invalid credential. The first
command after a token-mode server restart no longer fails with a 401.

### Startup waits visibly on an unreadable state directory (#304)

Before it starts the backend, `shed-server` now reads each of the active backend's state
directories once (`images_dir`, `instance_dir` and its parent, `snapshots_dir`, `uppers_dir`
and `socket_dir`) and logs `Checking state directories: …`. A startup step stalled on the config
or a state directory logs a line naming the path after 10 s, then every minute:

```text
shed-server: startup is still waiting on /Volumes/ext/shed/vz (checking state directory) after 10s. …
```

On macOS the line points at the permission prompt for an external drive and at Full Disk
Access; on Linux it says the filesystem may not be responding. Startup continues on its own
once the directory can be read. A directory macOS has denied gets one warning with the Full
Disk Access fix. The probe is not fatal, but a later step that needs the directory can still
fail.

This changes one failure mode. A server whose store hangs on a read (an unanswered prompt, or a
filesystem that is not responding) now blocks startup at that line and does not reach
`Shed server is ready` until the read completes. Before, it reached `ready` when egress was
off, and only the background resume of running sheds hung, with no message. See
[Image store on an external drive](../reference/vz-operations.md#image-store-on-an-external-drive).

### `server.yaml` is no longer a dpkg conffile (#109)

The `shed-server` deb used to ship `/etc/shed/server.yaml` as a dpkg conffile. If you had
edited it and a release changed the packaged template, dpkg prompted. An unattended upgrade
(`apt-get -y` with no terminal) failed at that prompt with `end of file on stdin at conffile
prompt` (exit 100) and left the package unconfigured.

| Operation | Behavior from 0.9.1 |
|-----------|---------------------|
| Fresh install | Creates `/etc/shed/server.yaml` from `/usr/share/shed/server.yaml.default`. |
| Upgrade, reinstall, remove | Never prompts about `/etc/shed/server.yaml` and never changes it. |
| Purge | Deletes `/etc/shed/server.yaml`. The host key and TLS files in `/etc/shed` stay. |

- **The first upgrade to 0.9.1** marks the old conffile entry `obsolete` in dpkg's database
  (`dpkg-query -W -f='${Conffiles}' shed-server`). This is harmless; dpkg leaves the file alone.
- **The reference copy** is `/usr/share/shed/server.yaml.default`, and every upgrade updates
  it. Your config no longer picks up template changes, edited or not; the server supplies a
  default for any key your config leaves out. To see what a release changed:

  ```bash
  diff /usr/share/shed/server.yaml.default /etc/shed/server.yaml
  ```

- **A host stuck by this failure** shows `iU` for `shed-server` in `dpkg -l` and has an
  `/etc/shed/server.yaml.dpkg-new`. Installing 0.9.1 as in
  [Linux server (apt)](#linux-server-apt) recovers it: your config is kept and the leftover
  `.dpkg-new` is removed.
- **Rolling back to 0.9.0 or earlier** registers the file as a conffile again, so dpkg asks
  about an edited config. Keep yours without a prompt:

  ```bash
  sudo apt install --allow-downgrades -o Dpkg::Options::=--force-confold shed-server=<version>
  ```

  The next upgrade marks the entry obsolete again.

### shed-server ships as a signed ShedServer.app (#304)

On macOS, the brew formula now installs `shed-server` inside a Developer ID signed app bundle,
`$(brew --prefix)/opt/shed/libexec/ShedServer.app` (bundle ID `ai.stridelabs.shed-server`).
`bin/shed-server` is a symlink into it, and the brew service still runs
`opt/shed/bin/shed-server`, so existing launchd plists stay correct and the normal upgrade
restart is all that is needed. The formula no longer re-signs `shed-server` ad hoc on install.

macOS keys a bare binary's privacy grant on its absolute path, and brew's Cellar path changes
every version, so an external drive's permission was asked again after every upgrade. A bundle's
grant is keyed on its bundle ID and signature, which are the same for every build, so it
survives upgrades.

The cost is one more prompt, once: the first time the server starts as `ShedServer.app`, macOS
asks again for the external drive, because the identity changed. After that, upgrades don't ask
again unless the grant is revoked or reset. If the server is started from Terminal rather than
the brew service, the prompt names Terminal. See
[Image store on an external drive](../reference/vz-operations.md#image-store-on-an-external-drive).
