# Upgrade Guide: v0.10 to v0.11

v0.11 changes how credentials get into a shed. Until now a shed's SSH agent, AWS credential endpoint and Docker credential helper asked your machine for each use, and the desktop app held an Approvals queue for the answers. All of that is removed. A shed now receives what it needs once, at create or when you run `shed provision`, as ordinary files and environment variables, from the desktop app on the machine you chose. The credential bus itself stays; shed just no longer ships anything on it.

This is a **clean break**, as v0.10 was: nothing migrates old state, and no compatibility layer keeps the removed helpers working.

!!! warning "Existing sheds keep running, but get nothing new until recreated"
    A shed created before v0.11 keeps running with the image it was made from. It still has the three helpers, and they will find no listener to ask, so they fail. Nothing in it is migrated, and delivery does not reach an old image: its agent is too old to take items, so `shed provision` skips both delivery stages as `image_too_old` and says to recreate the shed. **To get delivered credentials, recreate the shed from a v0.11 image.**

    To keep using an old shed meanwhile, switch its helpers off so tools stop asking them. With the helpers' listener gone, Docker's `credsStore: shed` makes every pull fail, public images included, and `SSH_AUTH_SOCK` points at an agent that answers nothing:

    ```bash
    sudo systemctl disable --now shed-ext-ssh-agent.service shed-ext-aws-credentials.service
    sudo rm /etc/environment.d/shed-extensions.conf   # SSH_AUTH_SOCK and the AWS endpoint
    # remove the "credsStore": "shed" line from ~/.docker/config.json
    ```

    Log in again (or restart the shed) so new sessions drop the old variables.

## Before you upgrade

- **Remove `ssh-agent`, `aws-credentials` and `docker-credentials` from `extensions.enabled` first.** A v0.11 server whose config names one fails to load and does not start (section 2).
- **Upgrade the server and the desktop app together.** A v0.11 server asks your pinned machine for a delivery; a v0.10 app holds the pin but never answers, so every create ends `source_offline` and its install hook waits for `shed provision`. A v0.11 app against a v0.10 server has no delivery to use, and the v0.10 helpers have no broker to ask.
- **If you ran the v0.10 app, your pin is kept** (section 4). Run v0.11 on the pinned machine, or move the pin to the machine you will use. A pin whose machine is asleep or gone holds back every create's install hook until `shed provision` runs with a source connected, even with no provider enabled. To stop that, move the pin, or clear it with `shed source unbind`: with no pin a create asks no source and runs its install hook. The next of your machines to connect is bound again (see [Credential Source](../extensions/source-binding.md#clearing-the-source)).

## What changes

- **Credentials are delivered, not brokered.** The desktop app answers a server's request with the files and variables its providers hold (SSH key, GitHub token, API keys, an envsecrets login, named files). Nothing is asked per use.
- **The image `extensions` is now `full`.** Two variants remain, `base` and `full`.
- **The three credential helpers are gone**: `shed-ext-ssh-agent`, `shed-ext-aws-credentials` and `docker-credential-shed`, with the Go code behind them and their guest units.
- **Approvals are gone from the desktop app.** There is no approval pane, badge, banner or tray list, and no approval, signing or notification policy.
- **The desktop sidebar has four entries**: Sheds, Agents, Activity and System. Activity lists server events from every server you have configured; a shed's egress shows in its detail; egress profiles are listed in System.

## 1. Images: `extensions` becomes `full`

`ghcr.io/charliek/shed-vz-extensions` and `shed-fc-extensions` are no longer built. The variants are:

| Variant | Contents |
|---|---|
| `base` | the base OS, roost-session and craze |
| `full` | `base` plus `strix`, `prox`, `parcel` and `envsecrets` |

Because `extensions` is gone, **`--image extensions` is now an unknown alias**, and the server no longer synthesizes it. An image store that pulled the old image still holds a label named `extensions`; the server ignores it for `--image`, and `shed image rm extensions` removes it so `shed image prune` can free the old image once no shed uses it. Change every place that names it:

| Where | Change |
|---|---|
| A server config's `default_image` or `image_aliases` naming a `...-extensions` ref | use `ghcr.io/charliek/shed-vz-full:${shed.version}` or `shed-fc-full`, or drop the key to take the default (`full`) |
| A script or alias that runs `shed create --image extensions` | use `--image full` (or `--image base`) |
| An image you built `FROM` a `...-extensions` image | rebase it on `shed-vz-full` / `shed-fc-full` (the four apt tools are there) or on `base` |
| A remote (cloud) server's `default_image` and `image_aliases` naming a cloud image family, including one in a private env file | change the family to `family/shed-full-amd64` (or `family/shed-base-amd64`) |
| A cloud image bake you run yourself | bake with `--variant full` (the default) or `--variant base`; the image family is named `shed-<variant>-<arch>` |

Rebuild any cloud image first: an existing `shed-extensions-amd64` family has the old helpers and an old agent protocol. `strix`, `prox`, `parcel` and `envsecrets` come from the apt repository and are not pinned, as `strix` and `prox` were not before. `mise` stays, but no longer installs envsecrets.

## 2. The three helpers and `extensions.enabled`

The names `ssh-agent`, `aws-credentials` and `docker-credentials` can no longer be enabled. A server config that names one **fails to load**, from the server and from the CLI, with this message (the name is the one you wrote):

```text
extension "ssh-agent" was removed in v0.11 and can no longer be enabled; remove it from extensions.enabled (see docs/upgrades/v0.10-to-v0.11.md)
```

Remove those names from `extensions.enabled`. Every other name still loads: the generic [extension mechanism and the credential bus](../reference/extensions.md) are unchanged, and `shed-server doctor` stops expecting the retired manifests. A cloud (remote) server was already refused any `extensions.enabled`.

New sheds no longer have:

- the SSH agent socket: `SSH_AUTH_SOCK` is not set by the image;
- the AWS credential process: no `AWS_CONTAINER_CREDENTIALS_FULL_URI` and no endpoint on port 499;
- the Docker credential store: no `{"credsStore": "shed"}` in the Docker config.

Anything that depended on them needs a delivered key or an ordinary sign-in inside the shed. See [Credentials in a shed](../guides/credentials-in-a-shed.md) for AWS and registry sign-in.

## 3. Set up delivery

1. **Install the v0.11 desktop app** on the machine whose credentials the shed should hold. The app is the credential source; there is no separate daemon.
2. **Open Preferences → Provisioning**, and turn on the providers you want and set their `only` rules. Give every provider an `only.servers` list. A provider that is on with no `only.servers` delivers to any server in your shed config that asks. See [Desktop provisioning](../desktop/provisioning.md).
3. **Check the preview** in the same section for a shed name on a server: it lists each item, size and fingerprint and never a value.
4. **Create a shed.** `shed create` asks your source once, writes stage 1 before the clone, clones, writes stage 2, and runs the install hook.
5. **Finish or repeat a delivery with `shed provision <name>`**, which also re-delivers after you change a setting or an item expires. `shed provision <name> --status` prints what the shed holds and what it is owed.

The machine identity and certificate store under `<state>/broker/` keep their paths: an existing `machine.json` is used as it is, and no machine becomes new because of this release.

Read [Credential delivery](../reference/delivery.md) for the steps, the record and the failure warnings.

## 4. The pin: which machine is asked

The server asks **one** of your machines for your sheds' delivery: your **pin** on that server. It is set automatically by the first desktop app that connects for you, and the app opens a stream to every server in your shed config, so the first of your machines to sign in to a server becomes your source there. To move it:

- Preferences → Provisioning → **Use this machine** on that server's row, or
- `shed source use <machine>` (the app's IPC op is `source.use`).

To clear it, run `shed source unbind` (new in v0.11; an admin can add `--user`). The server forgets the pin and the machines it remembered for you, and the first of your machines to connect next is bound again, so a desktop app that is still running takes it back within about 30 seconds: quit the app first if you want no source. An existing pin from v0.10 is kept. A server with no bound machine for you sees no request and no warning, and a create behaves as it did before delivery. See [Credential Source](../extensions/source-binding.md).

## 5. An offline source holds back the install hook

When your pinned machine is not connected (the laptop is shut, the app is quit), a create still makes the shed and starts it, but ends with the fixed warning:

```text
Credentials were not delivered (source_offline). Run: shed provision <name>
```

The install hook, and the startup hook that follows it on create, do not run, **even for a public repository**: the hook may need what delivery brings, and it runs once. They run when you connect the source and run `shed provision <name>`. The startup hook still runs on every later start. A create can also wait up to `delivery.timeout` (30 seconds by default) for a connected source that is slow.

## 6. What stops working

- **Approvals and prompts.** There is nothing to approve per use. A delivered credential is usable by anything in the shed while it runs, a coding agent included. There is no signing check any more. See the trade stated in [Credentials in a shed](../guides/credentials-in-a-shed.md#the-trade) and in [Security](../reference/security.md).
- **Per-shed overrides, SSH signing policy, AWS and Docker modes, and the broker audit log** in the desktop app's Preferences are removed. Activity now reads the server's own `/api/activity`, which is why it needs the server's audit log (on by default in `mtls` mode).
- **Touch ID and the Linux polkit approval** are gone; the `.deb` no longer ships the polkit policy.
- **`shed-host-agent`, the old broker, `extensions.yaml` and its audit log** have no successor. You can delete a leftover `extensions.yaml` and `extensions-audit.log` beside it; the audit log holds shed names, key fingerprints and registry names.

## 7. Check it worked

```bash
shed create demo --repo example/widgets --image full   # delivery runs with the create
shed provision demo --status                           # the record: steps and items
shed exec demo -- ls -l /home/shed/.ssh             # the delivered key, if you enabled ssh-key
```

A `base` shed has roost-session and craze but not the four apt tools; both variants run delivery.
